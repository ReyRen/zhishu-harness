# 工作台概念参考

本文记录在官方 DeepSeek Harness 上增加「工作台」时要守住的概念和边界，供后续开发对照。概念来自 [dsh-desktop](https://github.com/dataelement/dsh-desktop) 相对官方客户端多出来的工作台市场和业务面板，对照实现主要在该仓库的 `packages/dsh-desktop-workbenches/`、`build/dsh-desktop.patch.yml`，以及它对官方侧栏、会话包打的插槽补丁。

智枢桌面端现在不是这条路。它是官方 Harness 壳，业务是盖在对话页上的 model 站点，两边存储互不相通，见 [desktop-secondary-development.md](./desktop-secondary-development.md)。官方 DeepSeek 桌面端也没有工作台宿主。本文不要求把 `dsh-desktop` 整包搬进来，也不替换现有的平台站点。

## 它解决什么问题

官方 Harness 的界面是通用会话：一段对话、一个工作区目录、一组插件。一个具体业务（写稿、选址、看板）没有自己的界面、自己的记录，也没有「只属于这件事」的对话。

工作台把三样按一个业务收在一起：

- 一块业务界面
- 只属于这个工作台的会话
- 这个业务自己的数据

AI 仍使用 Harness 里原来的 Agent，不另做一套模型或聊天框。

## 两层插件

工作台市场页和每一张业务卡片不是同一个包。

**宿主插件**负责公共能力。在 `dsh-desktop` 里它是 `dsh-desktop-workbenches`，由桌面自己的补丁插入插件树，数据目录是 `dshHomePath('desktop-workbenches')`。它提供：

- 侧栏上的「工作台 / 会话」切换，以及工作台市场主面板
- 服务 `desktopWorkbenches`，供业务包注册面板
- 本机接口 `/api/desktop-workbenches/*`：市场目录、安装卸载、收藏和当前工作台等状态
- 包住官方会话的外框。没有打开工作台时，外框直接退回原来的对话

市场列表读的是已发布目录（`dsh-desktop` 使用 `https://market.dshdesktop.com/index.json`），不是把业务包打进宿主。点安装时，浏览器只提交目录条目的身份，服务端按目录里钉死的包名和版本交给官方 Plugin Manager 的 `installBundle`。安装记录和界面状态分开记：前者说明这个包从哪来，后者记已添加、固定、收藏、当前工作台和会话归属。

**业务工作台**自己也是一个 DSH 插件，并且一个包只放一个工作台。它同时是：

- 一个 npm 包
- 一个 bundle：`package.json` 声明 `dsh.bundle.patch`，用 `cordis.patch.yml` 把服务端插进插件树
- 一个面板：客户端调用 `desktopWorkbenches.register({ title, ... }, Component)`

客户端必须先依赖宿主。`dsh.client.inject` 里要包含宿主包名，这样 `desktopWorkbenches` 先于业务客户端出现。服务端如需判断「这段会话属于谁」，注入只读服务 `desktopWorkbenchOwnership` 并调用 `read()`，不要从界面或私有设置推断。

身份不要混用。安装用 npm 包名；插件树用 `cordis.patch.yml` 里的条目 id；侧栏、市场卡片和会话归属共用工作台身份。有真实 GitHub 仓库时，身份是小写 `owner/repository`。只在本机使用、没有仓库时，宿主按真实客户端包名生成 `local:<npm 包名>`。新包不要自己填 `register({ id })`。

一个坏掉的业务包不能拖垮 Harness。`dsh-desktop` 把客户端依赖了工作台宿主的包标成工作台，启动失败不当成致命错误，只在工作台管理里显示包名、阶段和原因。

## 怎么挂进官方界面

官方界面没有「工作台」这两个字。`dsh-desktop` 不重写前端，只给官方包补插槽，再由宿主插件占住：

| 插槽 | 作用 |
| --- | --- |
| `sidebar.quickSwitcher` | 品牌区和面板列表之间的「工作台 / 会话」切换 |
| `main` 上 key 为 `desktop-workbenches` 的面板 | 市场页。点侧栏「工作台」时 `selectPanel` 切到这里 |
| `desktop.workbench.frame` | 包住官方 `main.conversation`。打开某个工作台后，在这里放业务面板和原生会话 |

市场页（搜索、市场 / 收藏 / 已安装、卡片、安装按钮）全是宿主画的。点进某个已安装工作台后，主区域才换成该业务包注册的组件。

布局有两种，按主任务选，不要默认旁边永远钉着一块聊天：

- **业务整页**（`customFrame: true`）：审核、报表、看板等以业务为主。需要 AI 时，把宿主传入的 `conversation` 节点放进自己的布局。不要自己再做一套聊天界面，也不要一进入就自动建会话。
- **标准分栏**：对话是主任务，业务是旁边的状态或工具。默认左侧原生会话，右侧业务区约占 36%，可用 `layout.businessSide` 和 `layout.businessWidth`（0.25–0.7）调整。

没有绑到当前工作台的会话时，业务面板仍然要能用。浏览、建档、选项目不能以「已经打开一段对话」为前提。

## 会话、工作区和业务数据

- 一个工作台可以有多段会话，每段会话最多属于一个工作台。
- 工作区仍是用户选的项目目录。同一工作区里可以有原生会话，也可以有不同工作台的会话。
- 业务自己的档案、项目不等于 DSH 工作区。玄学档案、选址项目可以继续用各自原来的创建流程。
- 工作台模式的侧栏只显示当前工作台的会话。新建会话时创建并绑定一条新的，不把已有的普通会话改绑过来。
- 切回「会话」只显示未绑定的原生会话。
- 卸载或关掉工作台后，已有会话、项目文件、笔记和收藏保留。

打开工作台时，宿主会记住当前工作台，并在侧栏里过滤会话和工作区。业务包通过宿主提供的方法创建或恢复会话，由宿主登记归属。

## Agent 在里面做什么

Harness Agent 仍是这段会话里的执行者：理解请求、调用工具、改工作区里的文件、把话说回会话。它不画业务界面，也不决定业务数据存在哪。

业务界面负责把任务送进属于自己的会话，并决定结果怎么落地。依赖会话的操作（向 Agent 发请求、写草稿）发生时，才检查并创建或恢复本工作台的会话。开场内容写成草稿，由用户自己发送。需要自动跑的流程必须跑在归属正确的会话里，不能在工作台不可见时偷偷发送。

Agent 没有「答案显示完就自动回调业务」的钩子。要它写入业务系统，必须在这一轮里让它自己发出调用，或者由页面在回复落定后自己去存。

## 结果怎么回到业务

按「结果是什么、谁负责写入」选择，不按临时还是持久化选择。

| 方式 | 谁写入 | 适合 |
| --- | --- | --- |
| 工作区文件 | Agent 用文件工具改用户项目目录里的文件，页面再读 | 结果本身就是项目里的文件，例如一份 Markdown 或报表。这是项目文件，不是临时缓存，也不能当作远程库 |
| 插件工具（function calling） | 业务服务端 `ctx.tools.register()` 登记工具。模型在本轮决定调用后，Harness 执行其中的 `execute` | 要落成结构化数据。本地数据目录和远程后台都可以。入库优先用这种：正文放在工具参数里，页面再按同一份数据刷新 |
| 页面订阅会话事件再调后台 | 模型只在会话里回答。页面等助手消息落定后自己调接口 | 存不存、存哪一段由页面决定。页面要自己认出对应的那条回复 |

工具不是页面按钮的回调。按钮把请求送进会话；模型根据工具说明和这段请求决定调不调、参数填什么。`execute` 只能拿到参数，读不到会话里已经显示的文字。只写「帮我写一段作文」、却不要求调用保存工具时，模型经常只在会话里写完，不会入库。

页面拿回复时，不要读工作区目录，也不要打开会话持久化写的 `.jsonl`。工作区是项目文件。会话日志在 Harness 自己的会话存储根目录下，按项目路径分目录，是持久化后端的文件。页面应注入 `sessions`，对当前会话 `retain()`，订阅 `binding.eventSource`。这和会话界面用的是同一份事件窗口，里面有用户消息、工具调用、流式片段 `assistant/live-chunk` 和落定的 `assistant/message`。`binding.session` 只有是否还在跑等状态，没有正文。宿主渲染出来的 `conversation` 节点也只是界面，不会把正文当作 props 交下来。流式片段会不断进来，等这条助手消息落定后再保存。

规范里的 `/api/<工作台 id>/...` 是业务插件注册在本机 Harness 上的路由，页面用相对路径访问。远程库可以接在这条路由后面，也可以由页面直接请求。本地路由多出来的能力是能先核对会话归属，再去动远程数据。

## 前端技术栈

Harness 里用户能看到的界面是官方 React 18 客户端。Web 和桌面看到的是同一份界面：桌面用 Electron 打开本机的 Harness Web UI，不另写一套原生界面。Electron 主进程和插件服务端是 Node。

业务面板必须是这棵 React 树上的组件：

- 客户端打成一个已经构建好的 JS 文件，用 `window.__ModuleLoader__.load` 注册。宿主不会替你跑开发服务器，也不会去加载一个独立的 `index.html`。
- `require('react')` 使用 Harness 自带的 React，不要再打包第二份。
- 图表等其他库在构建时打进这个文件。`require` 除此之外只能拿到共享基线和 `dsh.client.external` 里声明的模块。
- Vue、Angular 组件不能直接传给 `register()`。宿主用 React 的 `createElement` 渲染第二个参数。现成的 Vue 页面只能挂进这个 React 组件里的一块 DOM，或用 iframe 打开；会话、工具和 `eventSource` 仍留在 Harness 这一侧。这不是规范里的接法。

官方桌面端目前没有 `desktopWorkbenches`，也没有上述插槽。同一份业务包放进官方客户端不会出现市场和面板。要有同样的能力，需要先在本仓库补上宿主插件和插槽；补完之后，面板仍然必须是 React 组件。

## 和本仓库现有做法的关系

左侧「插件」仍是官方的组合包市场：技能、工具、界面扩展。工作台是另一层。业务包首先要能被 `dsh plugin add` 安装，然后再向工作台宿主注册面板。

智枢现在的业务空间是 model 站点盖在对话页上，cookie 和存储与 Harness 分开。工作台若要做，业务界面跑在 Harness 页面内部，和会话共用同一棵前端，并用会话归属把对话隔开。两条路解决的问题不同，不要把平台整站塞进一个工作台面板，也不要为了工作台改掉现有的登录和站点切换。

后续如果在本仓库实现宿主，增量放在 `overlay/`，用自己的 `cordis.patch.yml` 插入，不要改官方 `cordis.patch.yml`。官方包只有在没有对应插槽时才补插槽，规则见 [plugin-secondary-development.md](./plugin-secondary-development.md)。市场目录、安装来源和是否预装哪些业务包，按当时的部署（公网、内网、一用户一容器）另定，不要默认采用 `dsh-desktop` 的公网市场地址。

## 实施顺序

在智枢里做同类工作台，分成两段，必须先做宿主。本仓库的官方界面里还没有 `sidebar.quickSwitcher`、`desktop.workbench.frame` 和 `desktopWorkbenches`。业务包要调用 `register()`，这些不存在就注册不上，侧栏也不会出现「工作台」。

**第一段是宿主。** 侧栏上的「工作台」点开后是市场列表，这是宿主画的入口，不是某一个业务面板。这一段要一起做完：

- 「工作台 / 会话」切换，以及市场主面板
- `desktopWorkbenches` 注册服务和会话归属
- 包住官方会话的外框，用来放业务面板和原来的对话
- 安装、启用、卸载业务包，仍走官方 Plugin Manager

不要把 `dsh-desktop` 的 `dsh-desktop-workbenches` 原样拷进官方壳。按本仓库的二次开发方式放在 `overlay/`，缺的插槽再补到官方界面上。市场可以先只列出本机已安装的工作台。公网目录、收藏和上架不是做出第一个业务面板的前提。

**第二段才是按场景写的业务插件。** 每个场景一个包，注册自己的 React 面板，并遵守会话归属。宿主的切换和外框能用之后，再加第一个业务工作台。
